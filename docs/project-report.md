# HOYA BIT 加密貨幣市場研究 Agent — 專案報告

> 本文對應簡報七段架構，內容以 2026-07-31 的程式碼實況為準。
> 每一節末尾都有「限制」小節；全文所有限制彙整於第八節。
> 撰寫原則：**寧可少宣稱，不可誇大**。凡是系統做不到的，都直接寫出來。

---

## 1. 提案介紹

### 1.1 我們解決的問題

加密貨幣研究者要判斷一個幣種的近期風險，通常要手動開十幾個分頁：交易所看價格與資金費率、
新聞網站看事件、Reddit 看情緒、區塊瀏覽器看鏈上活動、總經網站看聯準會動向。這件事本身很花時間，
但真正的問題在後面 —— **當你得出結論時，沒有人（包括你自己）說得清楚每一句話是從哪一筆資料來的。**

市面上的 AI 加密貨幣工具多半在解決前半段（把資料聚合起來、生成一段摘要），很少處理後半段。
生成式模型讓「產出看起來專業的分析」變得極為便宜，也因此讓「分辨這段分析有沒有根據」變得更加困難。

### 1.2 我們的定位

**Evidence-first 的加密貨幣研究 Agent**：輸入幣種與研究問題，在時間預算內整合 11 類資料來源，
產出一份**每個結論都能點回原始來源**的研究報告。

三個刻意的設計選擇構成我們的差異化：

| 選擇 | 一般做法 | 我們的做法 | 理由 |
|---|---|---|---|
| 結論方向 | 交給 LLM 自由生成 | 由證據訊號**加權確定性計算** | 同一批證據永遠得到同一個立場，可測試、可追溯、離線一致 |
| 反面意見 | 模型客套式的「但也需注意風險」 | 從本次訊號中**自動抽出反向的那一側** | 反證來自實際資料，不是語氣修飾 |
| 資料失敗 | 靜默略過或整體失敗 | 每個來源**獨立降級**並在執行記錄標示 | 使用者看得到哪一面向的覆蓋不完整 |

### 1.3 產出物

單次分析產生三個檔案，全部可稽核：

- `report.md` — 人類可讀的研究報告（立場、事實、推論、反證、風險、來源）
- `evidence.json` — 每一筆原始證據，含 URL、取得時間、可靠度分數、追溯欄位
- `execution_log.json` — 每一步的狀態、耗時、時間預算使用情形、降級紀錄

### 1.4 限制

- 這是**研究輔助工具，不是投資建議**，也不產生買賣訊號給使用者執行。
- 系統建立的是訊號之間的**同時性關聯**，不足以建立因果關係。
- 目前支援 BTC、ETH、SOL、BNB、XRP 五個幣種（輸入驗證會擋下其他輸入）。

## 2. 系統架構

### 2.1 設計原則：確定性 fan-out，LLM fan-in

我們刻意**不**採用「Router Agent → 多個 LLM 領域 Agent → Decision Agent」的多代理架構。
領域分工確實存在，但由**確定性程式**而非 LLM 承擔：

```
Orchestrator（程式碼路由，非 LLM）
├── 6 個領域採集 Agent（平行執行）  ← 新聞／社群／市場／技術衍生品／鏈上／總經
│     └── 共 11 個 Evidence Adapter  ← 確定性、可測試、可獨立降級、零 token
├── Strategy / Indicator Engine     ← Vegas 通道 + RSI + 加權訊號盤點
├── Evidence Validator              ← 結構與可追溯性檢查
├── Analyst Agent（1 次 LLM）       ← 證據 → 結構化推理
├── Critic Agent（1 次 LLM）        ← 稽核上一步，只能標註與下調信心
└── Report / Web Renderer           ← 報告、互動圖表、回測頁
```

採集 agent 平行執行後，總耗時等於最慢的 agent 而非所有來源加總：實測由 7.0 秒降至 3.0 秒
（未含全文爬取），含全文爬取時新聞 agent 成為瓶頸（約 5 秒）。

理由有三，都是可量化的：

1. **可驗證性**：adapter 不會幻覺，且被 117 個測試覆蓋。把它們換成 LLM agent 等於用可驗證性換架構圖上的名詞。
2. **成本**：LLM 領域 agent 的 fanout 會讓每次分析增加到 7–8 次呼叫。在免費方案每日 20 次的限制下，
   等於一天只能跑 2–3 次分析 —— 這在 Demo 當天是會出事的數字。目前每次分析用 3 次呼叫
   （推理、消息面摘要、Critic 稽核），約可跑 6 次。
3. **失敗面**：多一個 agent 就多一個會逾時、會被限流的元件。

### 2.2 執行流程（六個步驟）

| 步驟 | 說明 | 失敗時的行為 |
|---|---|---|
| `parse_input` | 幣種與問題驗證 | 拋出 `AgentInputError`，回傳 400 頁面 |
| `collect_evidence` | 6 個領域 agent 平行採集 11 個來源 | 單一來源失敗→降級證據（可靠度 0.20）並記錄 |
| `calculate_indicators` | 報酬、波動、RSI、Vegas 通道、訊號加權 | 缺資料的面向不產生訊號 |
| `validate_evidence` | 欄位完整性、ID 唯一性、可靠度範圍、時間格式 | 驗證失敗直接中止（不容忍髒證據） |
| `llm_reasoning` | Gemini 結構化 JSON 推理 | 失敗→確定性離線推理，狀態標為 `fallback:<原因>` |
| `critic_review` | 獨立稽核分析與其證據 | 失敗或配額不足→略過，報告其餘部分不受影響 |
| `generate_report` | 三個輸出檔 | — |

### 2.3 三階段時間預算

總預算 **720 秒（12 分鐘）**，分為三個獨立上限的階段，皆低於比賽的 15 分鐘限制：

| 階段 | 上限 | 內容 | 實測耗時 |
|---|---|---|---|
| ① 蒐集資料 | 7 分鐘 | 6 個 agent 平行採集 + 新聞全文爬取 | 約 5 秒（用掉 1.2%） |
| ② 整理與報告 | 3 分鐘 | LLM 結構化推理、指標、報告產出 | 約 0.3 秒 |
| ③ Critic 稽核 | 2 分鐘 | 獨立稽核分析與證據的一致性 | 約 0.1 秒 |

**上限是天花板不是目標**：每個階段做完就立刻進入下一階段，不會等滿。上限只在網路異常時才會觸發。

- 採集階段**每個來源之前**檢查 deadline。逾時的來源記為 `<label>:skipped:deadline`，
  與 API 失敗的 `<label>:fallback:<錯誤>` **刻意分開標示**，Demo 時能分辨「網路慢」與「API 掛掉」。
- 推理階段剩餘不足 **20 秒**、稽核階段剩餘不足 **15 秒** 時，該階段直接略過而非啟動後中途失敗。

### 2.4 技術選擇

**純 Python 標準函式庫，零第三方相依。** HTTP 用 `urllib`、XML 用 `xml.etree`、網頁用 `http.server`、
指標與 EMA 全部自己實作。這不是為了炫技，而是為了部署面：Lambda 打包沒有相依衝突、沒有 C 擴充編譯問題、
冷啟動快、任何評審 clone 下來 `python -m src.app` 就能跑。

### 2.5 限制

- **單體同步架構**：一次請求跑完全部流程。沒有佇列、沒有背景工作、沒有併發保護。
- **無持久化**：除了輸出檔與一個給大戶餘額比較用的本地歷史檔（`outputs-day5/whale_history.json`），
  系統不保存任何狀態，也沒有資料庫。重開即失去歷史。
- **無使用者系統**：沒有帳號、沒有權限、沒有速率限制。
- **12 分鐘的同步請求**：三階段上限加總為 720 秒。實測完整 live 分析約 6 秒，但若網路異常而用滿上限，
  瀏覽器與反向代理可能先行逾時。目前沒有背景工作或進度串流機制。
- **全文爬取僅涵蓋兩個白名單網域**（Cointelegraph、Decrypt）。其餘來源仍停在標題或導言層級。

## 3. 資料來源

### 3.1 來源清單（11 個採集器，皆免 API 金鑰）

| data_type | 來源 | 可靠度 | 內容 |
|---|---|---|---|
| `market` | CoinGecko market_chart | 0.90 | 14 天價格與成交量（337 點） |
| `news` | Cointelegraph／Decrypt RSS + Google News RSS | 0.60 | 5 則，含原文導言 |
| `macro` | alternative.me 恐懼貪婪指數 + Federal Reserve RSS | 0.80 | 全市場情緒 + 貨幣政策發布 |
| `announcement` | 各幣種官方 feed | 0.85／0.55 | 官方公告，含導言 |
| `onchain` | 各鏈公開 RPC | 0.70 | 鏈上狀態觀測值 |
| `social` | Reddit → Bluesky → Hacker News（依序降級） | 0.45–0.50 | 25 則貼文與情緒關鍵字 |
| `derivatives` | Binance 資金費率 | 0.75 | 費率與多空擁擠度 |
| `whale` | 已知大戶地址餘額 | 0.65 | 餘額 + 與前次查詢的增減 |
| `vegas_channel` | Binance klines + 策略引擎 | 0.70 | 4H 趨勢／1H 執行狀態 |
| `long_short_ratio` | Binance 大戶持倉多空比 | 0.70 | 24 點歷史 + 一致性 % |
| `tvl` | DefiLlama 鏈上鎖倉量 | 0.75 | 90 天日資料 + 30／90 天趨勢 |

另有一筆非 API 來源：

| `price_history` | 本地 5 年日線 CSV | 0.95 | 1826 天；14d/90d/365d/全期間的報酬、年化波動、最大回撤、價格區間分位 |

### 3.2 可靠度分數的意義

分數是**人工指派的常數**，代表「這類來源的證據強度」，並在三個地方實際發揮作用：
證據表直接顯示、降級證據一律重新標記為 0.20（絕不讓 fixture 的高分存活到代表失敗的證據上）、
以及訊號加權時社群類來源給予較低權重（0.4）而市場與衍生品較高（1.0–1.2）。

官方公告的可靠度**刻意分兩級**且在證據表中看得見：

- **第一方 feed（0.85）**：ETH（Ethereum Foundation Blog）、BTC（Bitcoin Optech）、SOL（Solana 官方新聞）
- **官方網域限定的新聞聚合（0.55）**：XRP、BNB。Ripple 與 BNB Chain 沒有可用的公開 RSS
  （`ripple.com/insights/feed` 為 404、`bnbchain.org` 回 HTML、Binance 公告 feed 在機器人防護後回 202 空 body），
  因此改用限定官方網域的 Google News feed —— 這是二手轉載，不是第一方來源，分數必須反映這件事。

### 3.3 消息面：白名單全文 + 導言 + 標題三級

這一點我們主動說明，因為它常被誤解。

Google News RSS 的 `<description>` **不含任何導言**，只是重複標題的一個連結加出版社名稱。
因此我們另外接入 Cointelegraph 與 Decrypt 的 RSS，它們每則附有 1–3 句原文開頭。
本次實測 5 則新聞中有 4 則帶導言（109–173 字元），官方公告帶 286–316 字元導言。

白名單網域的文章會進一步抓取正文（見 3.4）。因此摘要的素材分三級：**全文 > 導言 > 僅標題**，
提示詞要求模型依級別調整用語 —— 有全文與導言的可引用其中數字與機構名稱，只有標題的必須寫成推測
（「標題顯示…，但未說明細節」），且無論如何不得編造素材以外的內容。

### 3.4 限制

- **全文爬取僅限白名單網域**：Cointelegraph 與 Decrypt 的文章頁可取得 1,553–4,000 字元正文（實測 4 篇），
  且每次抓取前都會檢查 robots.txt。**Google News 的連結無法也不應抓取** —— 它是 JS 跳轉頁（抓下來 0 字元），
  且 `news.google.com/robots.txt` 對所有爬蟲全站禁止。因此來自 Google News 搜尋的項目永遠停在標題層級。
- 正文抽取以正規表示式進行（無第三方解析器），並用價格符號密度過濾掉媒體頁面的報價跑馬燈；
  這是啟發式作法，對版面特殊的文章可能失準。
- **社群來源可靠度最低（0.45–0.50）**，且情緒判斷僅依正負向關鍵字計數，不理解語意與反諷。
- **恐懼貪婪指數是全市場指標，不是單一幣種指標**，用於單幣分析時只是背景。
- **巨鯨追蹤僅支援 BTC/ETH/BNB**：SOL 與 XRP 沒有免金鑰、可驗證地址清單的餘額 API。
  且追蹤的是**已知大型交易所／機構地址**，不是全網即時巨鯨偵測。餘額增減為兩次查詢之間的差值，
  交易所錢包的流入流出成因很多，**不等同買賣方向**。
- **TVL 只涵蓋該幣自身的鏈**，對本身沒有 DeFi 生態的資產（如 XRP，TVL 約 3,200 萬美元）參考價值有限。
- **流動性使用成交額作為 proxy**，非訂單簿深度；免金鑰端點不提供買賣價差。
- **14 天窗口**是所有即時來源的共同期間；5 年 CSV 僅作長期脈絡，不參與指標計算。
- 本地 CSV 的 metadata 標示為 `public_fallback_not_organizer_package`（Binance 公開日線），
  涵蓋 2021-07-26 至 2026-07-25。

## 4. 推理設計

### 4.1 三層結構：訊號 → 立場 → 敘事

**第一層：訊號盤點（確定性）**

`_signal_inventory()` 把原始證據轉成帶方向與權重的訊號清單。每個訊號有 `side`（bull／bear／neutral）、
`text`（人類可讀的理由）、`evidence_id`、`weight`。權重反映來源強度，例如：

| 訊號 | 權重 | 依據 |
|---|---|---|
| 4H Vegas 通道多／空頭排列 | 1.2 | 技術面主要趨勢 |
| 資金費率擁擠度 | 1.1 | 衍生品實際成本，多空一方在付錢 |
| 期間報酬 > ±2% | 1.0 | 價格動能 |
| 1H RSI(6) 極端值 | 1.0 | 執行週期的超買超賣 |
| 恐懼貪婪指數極端值 | 0.9 | 市場情緒 |
| 大戶持倉過度偏斜 | 0.9 | 反向風險 |
| 風險偏好方向 | 0.8 | 總經背景 |
| TVL 30 天趨勢 | 0.7 | 慢速基本面，佐證而非擇時 |
| 社群情緒 | 0.4 | 低可靠度來源 |

中性訊號（例如「4H 與 1H 方向不一致」、「資金費率接近平衡」）**不計入方向門檻的分母**，
只出現在敘事層：離線推理會把它們列為「未定訊號」，說明它們不提供方向資訊、僅影響信心水準。

**第二層：立場判定（確定性）**

`_market_stance()` 把訊號加總為離散標籤：

- 方向性總權重需達 **1.5** —— 否則「證據不足以形成方向判讀」，一律中性
- 單邊淨優勢需超過 **25%** —— 否則「方向不明確」，一律中性
- 通過門檻才給出偏多／偏空，並附上權重最高的前 3 項推力與其 evidence ID

**這一層刻意不交給 LLM。** 若讓模型自由生成立場，會失去三件事：可重現性（同樣證據應得同樣結論）、
可測試性（門檻行為可用單元測試釘住）、離線一致性（無 LLM 時結果相同）。

**第三層：敘事推理（LLM）**

Gemini 以 JSON Schema 強制結構輸出：`market_judgment`、`confidence`、`facts[]`、`inferences[]`、
`conclusion`、`counter_evidence[]`、`observation_points[]`、`cited_evidence_ids[]`。

輸出後有一道**引用檢查**：若模型引用了不存在的 evidence ID，該次推理直接判定失敗並退回離線路徑。
這是防幻覺的最後一道閘門。

**第四層：獨立稽核（LLM）**

`critique_with_llm()` 是**第二次獨立呼叫**，輸入是完成的分析與其證據，任務是攻擊它。刻意不做成
分析 schema 的一個欄位 —— 同一次生成裡要求模型既下結論又批評自己，它會給自己寬鬆的評價。

稽核檢查五類問題：`over_claim`（結論強度超過證據）、`unsupported`（主張無對應證據）、
`ignored_counter`（反證存在卻未反映）、`stale_or_weak`（把低可靠度或降級證據當確證）、
`confidence`（信心與衝突程度不相稱）。

**稽核的權限被刻意限制**：它只能標註問題與**下調**信心（`confidence_adjustment` 限制在 -1 到 0，
正值會被拒絕），不能改寫結論。會改寫的稽核等於第二個分析師，讀者就失去了獨立檢查。
稽核若引用不存在的 evidence ID，整份稽核會被丟棄（與推理層同一道防線）。

### 4.2 離線推理不是佔位符

無 LLM 時的 `_offline_reasoning()` 使用同一份訊號盤點，產生完整的判斷、推論與反證：
支持方訊號成為推論、反方訊號成為反證、未定訊號調整信心。信心分數由公式計算：

```
confidence = clamp(0.30 + 0.35 × 一致性 − 0.06 × 來源失敗數, 0.20, 0.85)
```

因此離線報告仍然「會論證」，而不是列舉數字。這也是 Demo 第三層（完全離線）能成立的原因。

### 4.3 Prompt 成本控制

送給模型的證據**會移除長數列**（prices／volumes／dates／history 等超過 12 筆的數值序列），
替換為點數註記；文字類內容（新聞條目、導言、社群貼文）完整保留。
模型不需要 337 個逐點價格，它需要的是衍生統計。此舉將 prompt 從 62,016 字元降到 21,208 字元（**減少 66%**）。

### 4.4 限制

- **權重是人工設定的先驗值**，沒有經過最佳化或統計驗證。它們代表團隊對來源強度的判斷，不是學習來的參數。
- **立場門檻（1.5／25%）同樣是人工設定**，未經敏感度分析。
- **信心公式是啟發式**，不是機率校準（0.7 的信心不代表 70% 的正確率）。
- **LLM 每次分析消耗 3 次呼叫**（推理、消息面摘要、Critic 稽核）。免費方案每日 20 次，
  即每天約 **6 次**完整分析；用罄後三者各自降級並在頁面明確顯示原因。這是目前最緊的營運限制。
- **Critic 的實際 API 路徑尚未在真實配額下驗證**：schema 解析、信心調整、失敗降級、
  拒絕不存在的 evidence ID 都有單元測試覆蓋，但完整的 Gemini 往返因配額用盡而未能實測。
- LLM 輸出僅檢查結構與引用有效性，**不檢查語意正確性**。

### 5.2 畫面與敘事重點

**研究摘要頁** — 固定順序：結論 → 已確認事實 → 推論 → 反方證據 → 信心與限制 → 資料來源 → **獨立稽核**。
立場徽章可展開推導過程；事實與推論句尾的上標數字對應來源清單，點擊連到原網站。
第 7 節顯示 Critic 的判定、逐條 finding（依嚴重度標色）與信心調整前後值；未執行時會說明原因。

**互動圖表頁** — 5 張純 vanilla JS 的互動折線圖（價格、5 年歷史、TVL、多空比、恐懼貪婪），
滑鼠移動即時顯示該點數值。最有說服力的對比在長期脈絡表：
ETH 近 14 天正報酬，但近 1 年 −50.27%、目前價格位於一年區間的**第 9 分位** ——
只看 14 天會得到相反印象。

**執行流程頁** — 三階段時間預算表（上限／實際耗時／用掉比例）、6 個平行 agent 的耗時與結果、
每個來源的狀態、watchdog 跳過紀錄。這一頁是「多 agent 平行」最直接的證據。

**回測頁（`/backtest`）** — 見 5.3。

### 5.3 策略回測

用 5 年日線資料對 Vegas 通道 + RSI 規則做 **walk-forward 逐根重放**：每一步只把 `candles[:i+1]`
餵給策略函式，因此**前視偏誤在結構上不可能發生**（測試中以截斷歷史驗證同一根產生同一訊號）。

ETH 結果（838 根測試日線，扣 0.1%／邊手續費）：

| 指標 | 數值 |
|---|---|
| 策略報酬 | −42.76% |
| 買進持有 | −46.94% |
| 超額報酬 | +4.18% |
| 交易次數 | **2 筆** |
| 最大回撤 | −58.08% |

五幣種對照：BTC +11.2%（vs −7.3%）、SOL −8.5%（vs −57.0%）、BNB +26.7%（vs −2.7%）、XRP −14.5%（vs +77.9%）。

**我們對這份回測的結論是：它不能證明策略有效。** 每個幣種只產生 1–3 筆交易，
這個樣本數無法區分「策略有邊」與「運氣」。我們展示它，是為了說明我們如何驗證自己的東西，
而不是為了宣稱績效。頁面最上方即以此為開場。

### 5.4 限制

- **回測的時間框架與線上運行不同**：線上以 4H 趨勢／1H 執行判讀，但 EMA987 通道需約 1000 根 K 棒暖身，
  唯一夠長的歷史是日線 CSV。因此回測衡量的是「同一套規則套在日線上」。
- **樣本數嚴重不足**（1–3 筆／幣），任何勝率與報酬率都應視為觀察而非統計結論。
- **已扣手續費但未計滑價與資金費率**；多空雙向變體需要合約，實務上還有資金費率成本。
- **單一標的、單一參數、單一段歷史**，未做參數敏感度或跨期間穩健性檢驗。
- 回測首次執行需 2–3 秒重放（之後快取），Demo 前應先開啟一次。
- **歷史回測不代表未來績效。**

## 6. AWS 架構與部署

### 6.1 部署形態

單一 Lambda + Function URL，以 CloudFormation（`aws/template.yaml`）定義，`aws/deploy.ps1` 一鍵部署。

| 資源 | 設定 |
|---|---|
| `AWS::Lambda::Function` | Runtime python3.12、**Timeout 900 秒**、Memory 1024 MB |
| `AWS::Lambda::Url` | AuthType **NONE**（公開） |
| `AWS::IAM::Role` | 最小權限，含 Secrets Manager 讀取 |
| Secrets Manager | LLM API Key，不進程式碼、Git 或 CloudFormation 明文 |
| CloudWatch Logs | 執行狀態、錯誤、延遲與 fallback 觀測 |

5 個幣種的 OHLCV CSV 隨部署包一起發布。

Timeout 設為 Lambda 上限 900 秒，必須大於協調器的 720 秒三階段上限 —— 先前設 300 秒時，
只要蒐集階段稍長就會被 Lambda 中途砍掉。

### 6.2 為什麼是 Lambda 而不是容器

單次分析是**低併發、短生命週期**的同步工作，且零第三方相依讓部署包極小、冷啟動快。
比賽情境不需要常駐運算。

### 6.3 限制與風險（此節全部為已知風險，非未來計畫）

- **Function URL 沒有任何驗證**（AuthType NONE）。任何人取得網址都能觸發分析並產生 API 成本。
  這是為了評審能直接點開而做的取捨；**比賽結束後應立即限制存取或刪除 stack**。
- **Lambda 同步逾時 900 秒**（Lambda 上限），配合 720 秒的三階段預算。實測一次分析約 6 秒，
  但若網路異常而逼近上限，同步 HTTP 請求會先被瀏覽器或反向代理切斷。
  正式產品的長工作應改用 Step Functions 或背景工作 + 輪詢。
- **無佇列、無併發保護、無冪等鍵、無成本告警**。目前單一 Lambda 可被重複觸發。
- **CSV 隨部署包發布會變舊**，且增加 artifact 體積；正式環境應改為 S3 上的版本化資料集。
- **公開資料供應商可能限流或改變 schema**，因此執行記錄與 fallback 是強制而非選配。
- **文件與實作有落差**：`docs/aws-architecture.md` 撰寫時以 OpenAI Responses API 為例，
  目前預設供應商為 Gemini（兩者皆支援，由 `LLM_PROVIDER` 決定）；該文的來源清單亦早於後續新增的
  衍生品、巨鯨、Vegas、多空比與 TVL 來源。
- 本地開發使用 `http.server`（`ThreadingHTTPServer`），**不適合生產**：無 TLS、無反向代理、
  無速率限制。

## 7. 商業價值與未來展望

### 7.1 我們認為真正的價值在哪

生成式 AI 讓「產出看起來專業的分析」變得幾乎免費，因此**稀缺的不再是分析，而是可稽核性**。
本專案的護城河不是資料來源數量（那容易被複製），而是三件難以事後補上的設計：

1. **每個結論可回溯到 evidence ID 與 URL**
2. **立場由確定性規則產生，可重現、可測試**
3. **系統主動提出反證與資料缺口，而非只給結論**

### 7.2 可能的應用場景

| 場景 | 說明 | 前提 |
|---|---|---|
| 交易所研究內容 | 為使用者提供有來源標註的每日市場簡報 | 需要內容合規審查 |
| 投顧／資產管理的研究輔助 | 分析師的初步資料整合與反面意見提示 | 需要人工複核，不可直接輸出給客戶 |
| 合規與稽核 | 「這個結論當時基於什麼資料」可被完整重建 | 需要保存 evidence.json 的持久化層 |

### 7.3 技術藍圖（依優先序）

**已完成（原列為短期／中期，現已進入產品）**
- ✅ 新聞全文抓取：白名單網域、robots.txt 檢查、報價跑馬燈過濾（見 3.3／3.4）
- ✅ Critic Agent：獨立的第二次 LLM 呼叫，只能標註問題與下調信心（見 4.1 第四層）
- ✅ 平行採集：6 個領域 agent 同時執行，採集耗時由 7.0 秒降至 3.0 秒（見 2.1）

**短期（賽後 1–2 週）**
- **在真實配額下驗證 Critic 的 Gemini 往返**（目前僅單元測試覆蓋，見 4.4 限制）
- 回測參數敏感度分析與跨期間穩健性檢驗
- 全文抓取的白名單擴充（目前僅 Cointelegraph、Decrypt 兩個網域）

**中期**
- 持久化層（結論隨時間的一致性追蹤：我們上週說偏多，這週改口了嗎？為什麼？）
- 長工作的非同步化：三階段上限 720 秒，若真的用滿，同步 HTTP 請求會先被瀏覽器或代理切斷
- ETF 資金流、GitHub 活躍度等尚未覆蓋的來源

**長期**
- 訊號權重從人工先驗改為資料驅動（需要足夠的歷史結論與結果標註）
- 信心分數的機率校準

### 7.4 限制與誠實的商業評估

- **本專案不具備任何預測能力的證據。** 回測樣本數不足，權重與門檻未經驗證。
  任何商業化都必須先解決「如何證明這套判讀比隨機好」。
- **資料來源全部為免費公開 API**，這是優點（零成本、可重現）也是天花板
  （沒有訂單簿深度、沒有機構級鏈上指標如 MVRV／SOPR、沒有 ETF 流向）。
  升級到專業資料源（Glassnode、Nansen、CryptoQuant）需要付費金鑰與相應的商業模式。
- **LLM 成本尚未建模**：目前每次分析 2 次呼叫，在免費方案下可運作，但規模化後
  token 成本會成為主要變動成本。
- **法遵風險未評估**：在多數司法管轄區，向公眾提供投資相關分析可能觸及金融監理。
  目前的免責聲明是必要條件而非充分條件。
- **無競品分析**：本報告未包含對現有產品（如各交易所研究部門、TradingView、Messari）的系統性比較。
